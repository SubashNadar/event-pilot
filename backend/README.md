# Event Pilot Backend

The FastAPI service currently exposes an in-memory event and planning API. It
returns deterministic plans so the React app can integrate before Azure OpenAI
and LangGraph credentials are configured.

When Azure OpenAI is configured in backend/.env, plan generation uses a
structured Azure model response and falls back to the deterministic plan if a
provider request fails.

When `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_SECRET_KEY` are configured, every
Azure plan-generation and budget-revision request is traced in Langfuse. The
event ID is used as the Langfuse session ID, making the related runs easy to
find during a demo. `LANGFUSE_HOST` is also supported for existing local
configuration; new setups should use `LANGFUSE_BASE_URL`.

## Run locally

Python 3.11 or later is required for the Langfuse SDK used by this project.

    cd backend
    export PATH="$HOME/.local/bin:$PATH"
    uv venv --python 3.11 .venv
    source .venv/bin/activate
    uv pip install --python .venv/bin/python -r requirements.txt
    uvicorn app.main:app --reload --port 8001

Open API documentation at http://localhost:8001/docs.

## Planning runs (streaming + recovery)

Plans are generated by a **run**: the LangGraph workflow executes as a background
task and streams every step to the browser over Server-Sent Events.

- Six specialists (Logistics, Finance, Schedule, Requirements, Marketing, Risk)
  run in parallel. With Azure OpenAI configured, each one is an LLM agent that
  calls its MCP tool and returns a structured report; without Azure they use the
  same tools with rule-based inputs.
- Each step is verified by a deterministic check before it counts as completed.
- When a step fails, the recovery assistant explains why and offers options; the
  run pauses (`interrupt()`) until the user picks an option, types their own
  instruction, or skips. Paused runs survive a backend restart (SQLite checkpoints
  in `data/checkpoints.db`).
- Events are stored in `run_events`, so the stream replays after a refresh or a
  dropped connection (`Last-Event-ID`).

To demo the recovery card, set `EVENTPILOT_FAIL_ONCE=venue_search` in `.env`, or
plan an event outside Bengaluru (the demo venue catalog only has Bengaluru venues).

## Dynamic brief intake

`POST /api/v1/chat/brief` runs one turn of the planning chat (LangGraph:
intake → validate → check → frame):

- The user can describe the whole event in one sentence ("Wedding in Bandra for
  200 guests on 14 Feb, budget 10 lakh"). Fields are extracted with LLM structured
  output when Azure is configured, otherwise with rules that understand Indian
  budget formats (₹10L, 10 lakh, 1.2 Cr), dates and catalogue cities and areas.
- Only missing fields are asked, and each question is worded around what is known
  ("What's the total budget for 200 guests in Bandra West, Mumbai?").
- Options come from `app/data/benchmarks.json`: budget bands for that event type,
  city tier and guest count, typical guest counts, dates after the usual lead
  time, and objectives for the event type.
- Answers are checked against the benchmarks (budget per guest, lead time, city
  coverage); warnings carry one-click fixes.

## Venue search (BM25 + semantic, fused with RRF)

`venue_search` (MCP tool) searches `app/data/venues.json` (44 sample venues in 8
cities): it filters by city (aliases such as Bombay, Gurgaon or Navi Mumbai),
capacity and a venue budget, then ranks with reciprocal rank fusion of BM25
keywords, semantic similarity, area match and price. Semantic search uses
`AZURE_OPENAI_EMBEDDING_DEPLOYMENT` when set (vectors cached in
`data/embeddings-cache.json`); otherwise it runs BM25 only and says so. When
nothing fits, `near_misses` explains why, and the recovery card offers the exact
fix (e.g. "Raise venue share to 42%").

Both data files are labelled sample data. Replace them with real venues and
quotes before real use.

## Endpoints

- POST /api/v1/chat/brief — dynamic brief intake (see above)
- POST /api/v1/events · GET /api/v1/events · GET/PUT /api/v1/events/{event_id}
- POST /api/v1/events/{event_id}/runs — start a run (`{"operation": "plan-generation" | "budget-revision", "budget"?}`)
- GET /api/v1/events/{event_id}/runs/latest
- GET /api/v1/runs/{run_id} — run status plus every event so far
- GET /api/v1/runs/{run_id}/stream — SSE (supports `Last-Event-ID`)
- POST /api/v1/runs/{run_id}/steps/{step_id}/resolve — `{"option_id"}` or `{"custom_text"}`
- POST /api/v1/runs/{run_id}/steps/{step_id}/retry · /skip · POST /api/v1/runs/{run_id}/cancel
- GET /api/v1/events/{event_id}/plan
- POST /api/v1/events/{event_id}/plan and /revisions/budget — blocking variants for
  older clients (failed steps are skipped instead of paused)

## Change the plan by chatting

`POST /api/v1/events/{event_id}/chat` takes plain words: "move dinner to 9 PM",
"add a shehnai at 7 PM", "make it 300 guests", "put ₹2 lakh into catering",
"switch to Vashi Grand Ballroom", "we need wheelchair access", or a question
("what's the venue?").

1. `app/agents/plan_edit.py` turns the message into a `PlanEdit` (LLM structured
   output; a rule-based parser when Azure OpenAI isn't set or the call fails).
2. `prepare` checks each change against the plan and the catalogue: the venue
   exists in that city and holds the guests (raising the venue share if its rent
   needs it), the agenda item exists, the budget line exists, the date is in the
   future. Anything it can't apply comes back as one clarifying question.
3. A `plan-edit` run re-runs only the affected specialists, with the plan the
   owner sees as the base, and keeps every other report ("Kept from the current
   plan"). Edits are applied in code, so nothing else drifts and they cost no
   LLM tokens.
4. When the run finishes, what changed ("Opening session: 10:00 AM → 10:30 AM")
   is posted into the same conversation. If a step fails its check, the run
   pauses with recovery options as usual and the chat says so. If the run stops,
   the brief is put back.

Only one run per event at a time: a chat change waits for the current run, and
`POST /events/{id}/runs` returns 409 while one is running.

## Saved conversations

Brief intake turns (`POST /chat/brief`) and plan chat turns are stored in the
`chat_sessions` and `chat_messages` tables. The frontend keeps the intake
session id in localStorage, so a refresh restores the conversation and the brief
so far. When the event is created, the session is linked to it
(`POST /chat/sessions/{id}/event`), and the plan chat (`GET /events/{id}/chat`)
continues the same history.

## Abuse protection

`app/core/guard.py`:
- per-client rate limits on write requests (`RATE_LIMIT_WRITES_PER_MINUTE`),
  with a tighter budget for endpoints that call the LLM or start runs
  (`RATE_LIMIT_LLM_PER_MINUTE`, `RATE_LIMIT_LLM_PER_DAY`); replies 429 with
  `Retry-After`. Reads are not limited. Limits are in memory, per process: use a
  shared store (e.g. Redis) when running several workers.
- request bodies over `MAX_BODY_BYTES` get 413; chat messages are capped.
- user text is cleaned (control and invisible characters removed) and screened
  for prompt-injection phrases; flagged chat messages get a polite redirect and
  never reach the LLM.
- every prompt fences user text in `<user_message>` tags with a rule to treat it
  as data, and fence characters inside the text are neutralised.

## EventPilot MCP server

A read-only MCP server with two groups of tools. Nothing here books, pays or
sends; guest messages are drafts that wait for the owner's approval.

Custom tools over EventPilot's own data:

| Tool | Used by | Data |
|---|---|---|
| `venue_search` | Logistics | `app/data/venues.json` (sample), hybrid BM25 + semantic |
| `vendor_search` | Finance | `app/data/vendors.json` (sample): catering per plate, decor, photography, sound and light, entertainment, mehendi, AV |
| `holiday_check` | Schedule | `app/data/holidays.json`: DoPT central government holidays for 2026 and 2027, major festivals, long weekends, wedding and exam seasons |
| `guest_message_draft` | Marketing | templates for invites, reminders and venue changes, with checks |
| `budget_validation`, `schedule_conflict_check`, `event_requirements`, `marketing_readiness`, `operational_risk_assessment` | the other agents | rules |

Free web services (no key, no sign-up), each with an offline fallback:

| Tool | Used by | Service | Fallback |
|---|---|---|---|
| `weather_outlook` | Risk & Operations | Open-Meteo: the forecast within 15 days, otherwise the same week over the last five years (archive) | climate notes in `app/data/places.json` |
| `travel_access` | Logistics | OpenStreetMap Nominatim (geocoding) and the OSRM demo router (road km and minutes to the airport and main station) | bundled coordinates, straight line × 1.35 at 25 km/h |

Terms to respect: Open-Meteo is free for non-commercial use (under 10,000
calls a day) and its data is CC BY 4.0, so keep the attribution the tool
returns. Nominatim allows at most one request per second and asks for an
identifying User-Agent (set `HTTP_CONTACT`). The OSRM demo server is for light
use only. Responses are cached in `data/http-cache.json`, and calls to each host
are spaced out. For production or commercial use, self-host Nominatim and OSRM
or take a paid plan.

Each agent runs its main tool through the bounded LLM loop, then its context
tools in code (no extra LLM round). A context tool that fails never fails the
step: the report says what it couldn't check.

Guardrails in `app/mcp/client.py`:
- each agent may only call its own tools (`TOOLS_BY_STEP`);
- at most `MAX_TOOL_CALLS_PER_RUN` calls per run, each with `TOOL_TIMEOUT_S`;
- identical calls within `TOOL_CACHE_TTL_S` reuse the earlier result;
- tool output is treated as data: long strings are cut and control characters removed.

Run it separately from the FastAPI API:

    cd backend
    python -m app.mcp.server

The default streamable HTTP endpoint is http://127.0.0.1:8000/mcp. When it isn't
running, the API runs the same tools in-process. Resources:
`eventpilot://venue-catalog`, `eventpilot://vendor-catalog`,
`eventpilot://holiday-calendar`.

## RAG Knowledge Base

Step 2 uses PostgreSQL with the `pgvector` extension for curated planning knowledge. Add the Azure embedding and PostgreSQL variables from `.env.example` to `.env`, then run this local-only ingestion command from `backend/`:

```bash
.venv/bin/python scripts/ingest_knowledge.py
```

The command reads `knowledge/*.md` and `knowledge/*.txt`, embeds their chunks with Azure OpenAI, and replaces chunks for each matching source. The public API intentionally exposes only `POST /api/v1/rag/query`; document ingestion will become owner-scoped after Auth0 is implemented.
